# Идентификация объекта по реестру

Ключ записи: страна + реестр + registration_id. ID площадки хранится отдельно.
Латинская C в российском номере вида C + 12 цифр нормализуется в кириллическую С;
исходный текст остаётся в evidence. Для других стран формат номера не подменяется российским.

Каждое свидетельство содержит source_url, source_text, checked_at и статус:
user_supplied — сообщил пользователь; source_observed — увидели на странице источника;
registry_verified — сверено с самим реестром. Последний статус автоматически не присваивается.

В live-batch require_registration=True: отсутствие независимо наблюдённого номера
на обеих площадках отправляет пару на проверку. Конфликт ключей блокирует gap всегда,
даже при совпадении названия и внутреннего canonical_id. Совпадение номера не отменяет
проверку номера, питания, отмены, оплаты, налогов и состава гостей.

Номер не копируется из реестра целевого отеля во все его предложения: это создало бы
ложное доказательство совпадения. У каждой площадки своё свидетельство.
Нет номера — unconfirmed, а не HOTEL_NOT_FOUND. Иностранные номера пока не собраны.

Пользовательский пример: Невский берег 122, С782026029186, ссылка Яндекса.
Исходная запись сохранена в config/registration-seeds.json. Яндекс вернул CAPTCHA.
Поиск также выявил другой номер С782025003929 у Russian Express:
https://r-express.ru/guide/russia/hotel/nevskiy-bereg-122/
Это кандидат на конфликт/историческую смену записи; причина не установлена,
поэтому автоматического объединения и утверждения о проверке государственного реестра нет.

Synthetic domain fixtures M1 сохраняют прежний режим для воспроизводимости эталонной
математики. Live batch всегда включает более строгую проверку регистрационных ID.
